The AI-assisted workflow

A repeatable six-step loop that turns requirement documents into a traceable suite. AI drafts every step — a human verifies every step. Never the other way around.

01 · INGEST

Documents → cases

AI

Drafts structured test cases with IDs from requirements / a CSV master sheet.

YOU

Reviews coverage, adds domain-only knowledge, enforces 1:1 traceability.

02 · DESIGN

Framework skeleton

AI

Proposes folder layout, config, fixtures and page-object boundaries.

YOU

Owns architecture, naming, markers and secret handling.

03 · GENERATE

Code from cases

AI

Writes page-object methods and test bodies from the drafted cases.

YOU

Reviews logic, applies markers (smoke · negative · boundary…), kills over-engineering.

04 · VERIFY

Selector pass

AI

Infers selectors from documentation — plausible, not trusted.

YOU

Re-reads every locator from the live DOM with probe scripts; only verified constants enter the code.

05 · TRIAGE

Failure analysis

AI

Reads traces and logs, proposes root-cause hypotheses and drafts probe scripts.

YOU

Runs the probes, takes measurements, decides: app bug · flake · test bug.

06 · REPORT

Close the loop

AI

Summarises runs and updates the evidence tables in the docs.

YOU

Signs off, files defects, decides what stays red on purpose.

Project spotlight — RFM Automation

End-to-end test automation for the RFID Master Generator web app: 16 application modules, 135 test cases, every test name carrying the TC-ID of its master-sheet row — so a report line maps 1:1 to a spreadsheet line.

What I built

  • One file per module — page object + test file for all 16 modules; a future app change is fixed by editing one file's constants.
  • Zero hardcoded selectors in tests — tests only call page-object methods.
  • RunRecorder bridge — after every test the recorder rewrites results.js + test_results.json, so the HTML sheet shows live Pass / Fail / Blocked while the run is still going.
  • Skip-don't-fail policy — missing data yields Blocked, not a false red, so the suite runs against any environment.
  • Probe toolkit — inspection scripts that re-capture URLs, headings, columns and modal flows from the live DOM whenever the app changes.

Case studies — where AI was wrong

Formula: symptom → AI hypothesis → evidence → verdict. The measurements decide, not the model's most confident sentence.

01 · “The four-second search”

Symptom
Quick-search in a list “sometimes doesn't filter” — roughly a third of runs, seemingly random.
AI says
“The click handler isn't firing — dispatch a synthetic keyup event.”
Evidence
Probes with a 2.0 s wait saw the filter land; the same probe at 1.5 s did not. Measured DataTables client-side latency: ~1.6 s on a 2-row table, ~4.0 s on a 1,150,551-row table. No ajax — the filter is pure client-side JS.
Verdict
TEST BUGA fixed 500 ms sleep against a genuinely slow widget.
Fix
table_search() now polls the DataTables info line + row count every 250 ms (max 15 s) instead of sleeping.
Lesson
A “flaky” test is usually a measurement problem. AI's hypothesis was plausible and wrong; the numbers were neither.

02 · “The wrong column”

Symptom
One rewrite test kept asserting against a literal - value.
AI says
“The API returned null — add a retry.”
Evidence
header_index("RFID") substring-matched “MOTHER RFID”, an earlier column in the header row. The test was reading the right row of the wrong column.
Verdict
TEST BUGLocator precision, not data.
Fix
Two-pass header matching (exact text first, substring as fallback), plus table scoping that excludes modal tables and the DataTables empty-state row — which the app relabels, so text-based exclusion had silently stopped matching.
Lesson
Assertions are only as good as the locator before them.

03 · “The AI found a real production bug”

Symptom
Two operator-management tests could never pass, on any machine.
AI says
“Flaky modal timing — increase the timeout.”
Evidence
Probe of the exact click shows pageerror: primedRef is not defined; the modal never receives its open class, and no network request fires at all.
Verdict
REAL DEFECTThe Production Lines feature is broken in the app.
Fix
Tests kept red on purpose as documented intended failures (TC-OP-008 / TC-OP-009), with the evidence archived next to them.
Lesson
Automation that goes green by skipping is automation that lies. Sometimes the best portfolio piece is a test that refuses to pass.

AI guardrails

The part that earns trust: what I refuse to let the model decide.

🛟

AI output is a draft, not a fact. Every selector and flow is re-verified against the live DOM by scripts I run, with the raw output archived as artifacts.

🔐

No secrets in prompts. Credentials live in environment variables; the model sees redacted config at most.

📏

Measurements decide root cause. Not the model's most confident sentence — a probe, a timestamp, a row count.

🏗️

I own the architecture. Naming, folder layout, markers, and the decision of what fails vs. what skips are human calls.

🟥

Known-bad stays red. I never let AI “fix” a failure by weakening an assertion or adding a blanket retry.

🧾

Evidence is written down. Every verified DOM fact lands in the README with the probe that proved it, so re-verification starts from facts, not memory.
